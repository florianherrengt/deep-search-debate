# Refine sessions

Refine sessions are private, owner-scoped records mounted behind session authentication. `POST /api/refine-sessions` creates a session from `{ prompt }` and immediately starts its one preparation investigation and first question batch. `GET /api/refine-sessions` lists the caller's sessions; `GET /api/refine-sessions/:id` returns a canonical snapshot.

A snapshot includes the immutable original prompt, session state (`clarifying`, `starting`, or `research-started`), batch history, current `draftAnswers`, preparation-search links, and the final research link once handed off. A preparing or failed batch has a `pendingBatchId`; `currentBatchId` is set only while a ready batch accepts answers. Draft updates use `PUT /:id/draft` with `{ batchId, answers }`. `POST /:id/batches` submits answers immutably and opens the next batch. `POST /:id/retry` explicitly retries a failed current batch. `POST /:id/research` atomically reserves and starts the ordinary standalone deep search. Mutations return `{ refineSession: snapshot }`.

Answers may select multiple candidate IDs and include free text. Missing answers and empty selections are stored as unanswered. Older batches are immutable. Repeating a batch submission or final handoff with the same IDs and answers is idempotent. A start request may carry the just-submitted previous batch ID if it races an Ask more request; the manager uses the latest durable answers and cancels the active preparation. A failed preparation remains failed until explicit Retry, including after restart.

Preparation searches are ordinary deep-search roots with an explicit `refine_search_links` association. Automated-research history exposes these as Refine-origin jobs. Generic root recovery excludes all Refine preparation links; the Refine manager resumes only active preparing work and leaves failed batches waiting for Retry. The final search is linked atomically to the session and remains an ordinary manual research root for startup recovery. Refine sessions become read-only after the durable handoff begins; the resulting research remains accessible through its normal deep-search route.

Each session runs one brief investigation: one round, at most two search queries, and at most two selected results per query. Preparation reads the selected search-result pages without following their links, synthesizes a concise source-backed evidence brief, and saves it as the final output in search history without correction or structured analysis. Every later Ask more batch reuses that completed session-owned brief. Question preparation cannot launch additional research. Final research uses the ordinary deep-search defaults and complete report pipeline.

All clarification stages, request rewriting and condensation, and generations owned by preparation searches use the user's current Small model assignment, including its provider and reasoning effort. The durable preparation link determines that role for new and resumed search stages. Final research keeps the ordinary prompt-based model roles. Each generation snapshots the current settings, so a model-settings update applies to the next stage.

Question preparation uses one `refine-generate-questions` Small-model call per batch. It receives the original request, the saved evidence brief, and all immutable submitted answers, including explicit unanswered records. Its strict output contains final question text, candidate labels/actions/consequences, and evidence references. The evidence catalog contains deterministic IDs for exact original-request paragraphs, selected candidate labels, supplementary answer text, and research paragraphs; assistant question wording and unanswered records are not evidence. Unknown references, malformed output, blank question/choice fields, duplicate questions, and duplicate choice labels fail without repair or application retries. Valid IDs resolve to canonical excerpt text before the generation and completed checkpoint commit. The server assigns question and candidate UUIDs and saves the ready batch. A completed canonical checkpoint is revalidated against the same source catalog and reused after restart. Failed batches wait for explicit Retry. Restart reconciliation settles orphaned running generation attempts before resuming active preparing batches; the one registered generation retains ownership checks and cancellation. The old need/decision taxonomy and its derived shared-state revisions are not maintained.

The user decides when to end clarification: empty or poor batches still leave both Ask more and Start research available. Every final handoff uses the selected Small model to rewrite the original prompt and all submitted answers into a standalone research request, including selected candidates, supplemental text, corrections, and explicit unanswered questions. Unanswered questions remain unresolved; the rewrite must not invent answers or user requirements. Research starts automatically after the rewrite succeeds, without a separate approval step. Preparation requests within the configured research limit still pass through unchanged; oversized preparation requests use the same condensation mechanism. The complete original prompt and immutable answer batches remain saved in Refine. Rewriting uses ordered source excerpts and a rolling brief under the existing summary-context limit, so unlimited batches do not create an unbounded model call. Each validated chunk is checkpointed with its generation; completed chunks are reused after failure or restart using the original saved clarification record.

Start reserves the final search and captures its source record before cancelling preparation. Rewriting and research preflight run outside the database transaction; the rewritten request is saved before the ordinary deep-search job starts. A condensation failure during preparation leaves that batch failed until Retry. A final rewrite or preflight failure restores the clarifying session with its immutable answers and Start research available for an explicit retry. Research does not fall back to the original record after a rewrite failure. Invalid structured output fails without repair, truncation, or automatic application retries.
